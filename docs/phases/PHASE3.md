# Phase 3 contract: Full analysis and assistant

Read `docs/BRIEF.md` ("Aerodynamics and performance engine", "Claude assistant"), `docs/ARCHITECTURE.md`, `docs/phases/PHASE2.md` (coordinate system, schema v2, Tier 1 engine) and `docs/ENGINE.md` (Tier 1 methods). This file adds to them.

**Acceptance (from the brief):** the validation suite passes and its report is viewable in the app; Analyse returns results, checks and ranked recommendations; the assistant explains them correctly.

## 1. Tools (all verified to install and run in this environment)

- **AVL** (Drela & Youngren vortex-lattice) through the `optvl` package (PyPI wheels for CPython 3.12, `from optvl import OVLSolver`). Build the AVL input as a file or input dict from the design; read total forces (`CL`, `CD`, `CDi`, `CDff`, `e`, `Cm`), stability derivatives (`get_stab_derivs`), neutral point (`Xnp`) and strip forces (span loading).
- **XFOIL** through the `xfoil` package already in the backend (Phase 2), at the actual Reynolds numbers of the wing root, MAC and tip and the tail, Ncrit 9 (configurable). Cache polars on disk under `{APP_DATA_DIR}/cache/polars/{airfoil}-{re_rounded}-{ncrit}.json`.
- `numpy`, `scipy`. No other heavy dependencies.

## 2. Server engine `backend/app/engine/`

- `geometry.py`: the same derived geometry as the Tier 1 TypeScript `buildGeometry` (Phase 2 section 1 coordinate system). Must reproduce `shared/fixtures/tier1_cases.json` geometry numbers to 0.1 % (tested).
- `avl_model.py`: design → AVL surfaces (wing with root/tip sections and airfoil files, twist and incidence; horizontal and vertical tail or V-tail panels; booms and fuselage as AVL bodies or omitted with a stated reason; elevator as a control surface on the tail for trim). Runs at the cruise lift coefficient (trimmed with the elevator to Cm = 0 about the CG) at minimum and maximum payload, and at the stall-speed check point. Returns CL, CDi, span efficiency, CLα, Cmα, neutral point, static margin, trim elevator deflection, span loading (for the structure check) and stability derivatives.
- `polars.py`: XFOIL polars at the operating Reynolds numbers; section `cl_max`, profile drag versus lift at the cruise point (strip-integrated across the span using AVL's local lift coefficients), with the Tier 1 table as fallback when XFOIL does not converge (reported).
- `drag.py`: parasite drag build-up for fuselage, nose bay, booms, stopped propellers (edge-on, factor stated), motor pods, tilt hardware, landing gear, tail; wing and tail profile drag from XFOIL; interference factors. Itemised table with sources.
- `propulsion.py`: motor model with Kv, winding resistance and no-load current (first-order DC motor: torque constant from Kv, losses I²R and I0·V), matched to a propeller model. Until Phase 4 supplies real parts, use generic propeller coefficient curves CT(J), CP(J) from the propeller diameter and pitch-to-diameter ratio, fitted to published UIUC propeller-database trends (cite the source and the uncertainty); when a part with `thrust_data` is selected, fit to that data instead. Solve the operating point at hover (each lift rotor carries its share of weight) and at cruise (cruise thrust = cruise drag) separately: rpm, current, voltage, efficiency, electrical power. Default motor parameters are sized by the same statistical rules as Tier 1 and are reported as assumed.
- `battery.py`: LiPo and Li-ion models: nominal and loaded voltage with an internal-resistance model per cell (values per chemistry with sources), usable energy with depth of discharge and reserve from settings, peak current at hover and transition against the pack continuous and burst rating (C-rate), voltage sag at peak, cell temperature note.
- `transition.py`: speed sweep from 0 to 1.3 × cruise speed. Tilt layouts: tilt angle schedule from 0° to `tilt.max_angle_deg`; at each speed, wing lift from AVL CLα and CL0, required rotor thrust vector to balance weight and drag, available thrust at full throttle; thrust margin and electrical power through the transition. Quad + pusher: lift rotors carry weight minus wing lift, pusher thrust must exceed drag with acceleration margin. Output: minimum thrust margin, the speed where it occurs, peak power and current, the transition speed range (wing carries ≥ 80 % of weight), and a pass/warn/fail.
- `structure.py`: wing spar root bending at the manoeuvre load factor × safety factor (from settings) using the AVL span loading, for the chosen carbon tube (a default tube sized by the engine until Phase 4: outer and inner diameter, layup, modulus and strength with sources) — stress against allowable with a stated knock-down, tip deflection; boom bending with full motor thrust at the motor station plus a vertical landing load; pass/warn/fail with the margin.
- `analysis.py`: orchestrates the above into one `AnalysisResult` (JSON) with every number as `{value, low, high, unit, label, explain, source}` like Tier 1, the itemised mass and drag tables, the mission profile, both payload cases, and the checks.
- `checks.py`: the brief's checks with clear pass/warn/fail and a plain message each: hover thrust-to-weight above the settings minimum; static margin inside the settings range at minimum and maximum payload; CG inside the allowed envelope for every nose-bay payload (sweep the payload range in five steps); stall speed below cruise by the settings ratio; battery current within rating at peak demand; MTOW under the design limit (warn from the warning mass, fail above the design limit, separate fail above the 25 kg legal limit); transition thrust margin; spar and boom structural margins. Each check names its threshold and the threshold's source from settings meta.
- `recommend.py`: sensitivity sweep. Nudge each key parameter by a small step in both directions (span ±5 %, root and tip chord ±5 %, aspect ratio at constant area ±5 %, airfoil alternatives from the library, fuselage width/height ±10 %, battery capacity ±20 % and cells in parallel ±1, propeller diameter ±1 inch-equivalent), re-run the fast path (AVL + drag + propulsion + mass; reuse cached polars), discard changes that make any check worse than warn or that break a currently passing check, and rank by endurance gained. Each recommendation: plain sentence ("Increase the wingspan by 90 mm (5 %): endurance +6 min (95–118 → 101–124 min) because induced drag falls; mass +40 g"), the parameter change, before/after key numbers, and a "Try as new version" payload (the full parameter patch).
- `scale.py`: scale to target weight. Given a new take-off mass, re-solve the same layout: keep the wing loading band appropriate for the target cruise speed and stall margin, choose span and chord for the cruise lift coefficient near the best L/D of the chosen airfoil, size battery for the target endurance, motors and propellers for the hover thrust-to-weight minimum, booms and spar for the structural checks, iterate mass to convergence, then run the full analysis. Output a before/after table with a plain "what changed and why" line per row (wing loading, speeds, motor class, battery class, structure). Never multiply dimensions by a single factor.

Performance budget: one full analysis under 20 s on the 1 GB machine (measure it; AVL runs are well under a second, XFOIL polars dominate the first run and are cached), the sensitivity sweep under 60 s. Fly machine memory goes to 2 GB in `fly.toml` this phase.

## 3. API and data

- Table `analyses` (migration `0003`): `owner_id`, `project_id` (cascade), `version_id` (nullable FK, `ON DELETE RESTRICT` per the Phase 1 policy, so a version with an analysis can't be deleted silently; the delete endpoint already maps this to 409 with a plain message, and the UI offers "delete its analyses too"), `kind` (`full` | `scale`), `inputs` JSON (parameters, mission, settings snapshot), `inputs_hash`, `status` (`queued` | `running` | `done` | `error`), `progress` (0–1 with a short stage label), `result` JSON, `error` text, `duration_s`, timestamps.
- A single in-process worker thread with a queue runs analyses one at a time (the machine has one CPU); results are reused when `inputs_hash` matches a done analysis.
- `POST /api/projects/{id}/analyses` `{source: "draft" | {version_id}, kind: "full"}` → 202 `{id, status}`; `GET /api/analyses/{id}` → status, progress and the result when done; `GET /api/projects/{id}/analyses` list; `POST /api/projects/{id}/scale` `{target_takeoff_mass_kg}` → 202 like analyses with `kind: "scale"`.
- `GET /api/validation` → the latest validation report (section 5); `POST /api/validation/run` re-runs it (owner only, takes under 2 minutes, runs on the worker).
- Settings document schema 2 (upgrader 1→2): adds `checks.manoeuvre_load_factor` (3.0), `checks.structural_safety_factor` (1.5), `checks.transition_thrust_margin_min` (1.3), `analysis.ncrit` (9); each with label, description and source in meta.

## 5. Validation suite

`backend/app/validation/` with a runner that produces a JSON report (stored in `{APP_DATA_DIR}/validation/latest.json` and also committed as a snapshot under `docs/validation/latest.json` by the test run) with, per case: name, what is compared, reference value and source, engine value, error %, tolerance, pass/fail. Cases:

1. Textbook: lifting-line / closed-form checks — elliptic and rectangular wing induced drag and span efficiency (AVL against Anderson's lifting-line results), lift-curve slope against Helmbold for AR 4, 8, 16; ISA density; momentum-theory hover power; Raymer flat-plate skin friction example.
2. AVL reference: rectangular AR 16 wing and a tapered swept wing, AVL results compared to published AVL/VLM values (cite) and to the Tier 1 estimates (Tier 1 within its stated uncertainty).
3. XFOIL reference: NACA 0012 at Re 1e6 against published XFOIL and wind-tunnel data (Abbott & von Doenhoff; Ladson NASA TM-4074) for CLα, cl_max and minimum drag; SD7037 against the UIUC low-speed wind-tunnel data (Selig et al., "Summary of Low-Speed Airfoil Data" vol. 1) at Re 200k.
4. Published designs (at least two): **Quantum Systems Trinity F90+** (MTOW 5.0 kg, span 2.394 m, cruise 17 m/s, endurance 60–90 min, battery mass 1.5 kg; sources: Quantum Systems datasheet) and **DeltaQuad Evo** (MTOW 10 kg, span 2.69 m, wing area 0.84 m², empty 4.8 kg, 6.8 kg with one battery, cruise ≈16.5 m/s, 6-cell 22 Ah semi-solid Li-ion per battery, endurance 244–272 min with two batteries; sources: DeltaQuad vehicle specifications page and operations manual). Model each in the tool from its published numbers (state every assumption for anything not published), predict cruise power and endurance, compare with the published endurance, and record the error. The tolerance for these is wide (±30 %) and the report says so plainly; the point is to show the size of the error honestly.

Viewable in the app: a "Validation" page linked from Settings and from the analysis panel, listing every case with its source, error and pass/fail, plus a re-run button.

## 8. Implementation notes (backend, as built)

Binding for the UI and later phases; they record the choices this contract left open.

**Worker.** `app/jobs.py`: one daemon thread drains a priority queue and runs engine jobs strictly one at a time (analyses first, then a waiting validation run). Image readings keep their own single-worker executor, so they are never queued behind an analysis. Progress is written to the `analyses` row at most once a second (a stage change after a quarter second). At startup rows left `running` (a crash) become `error` ("interrupted ... run it again") and rows still `queued` are queued again. A clean shutdown asks the running job to stop at its next progress report (it goes back to `queued` and runs after the restart), then calls `shutdown_solver_worker()`. Polar cache `{APP_DATA_DIR}/cache/polars`, report `{APP_DATA_DIR}/validation/latest.json`.

**Recommendations are part of the full analysis** (one job, not a second kind). The worker stores the analysis result as soon as it is ready with `result.recommendations = null`, stage "Finding improvements", status still `running` (progress 0.56); the sweep then fills `result.recommendations` (the `run_recommendations` output) and the status becomes `done`. The UI shows the results while polling and the recommendations when they arrive. An invalid design gets `recommendations: {valid: false, recommendations: [], message}`.

**Reuse.** `inputs_hash` = SHA-256 of kind, parameters, mission, the full settings document, engine and job versions (and the scale target). A finished analysis with the same hash is copied into a new `done` row at once (`reused_from_id`, stage "Reused an identical earlier analysis"); a job with the same hash still queued or running for the same project and source is returned instead of a new one.

**Endpoints.**
- `POST /api/projects/{id}/analyses` `{source?: "draft" | {version_id}, kind?: "full"}` and `POST /api/projects/{id}/scale` `{target_takeoff_mass_kg (0.2-25), source?}` → 202 list item `{id, project_id, version_id, version_number, source: "draft"|"version", kind, status, progress, stage, error, duration_s, inputs_hash, reused_from_id, queue_position, created_at, started_at, finished_at, headline}`. 503 plain while the worker is not running; 422 for a version of another project.
- `GET /api/analyses/{id}` → list item plus `target_takeoff_mass_kg` and `result` (full: the AnalysisResult plus `recommendations`; scale: the `run_scale` output). `GET /api/projects/{id}/analyses?limit=50` → list items, newest first (no `result`; `headline` = a few summary Quantities plus check counts once done).
- `DELETE /api/versions/{vid}` → 409 `{detail, analyses: n}` when the version has analyses; `?with_analyses=true` deletes them, then the version. Deleting a project deletes its analyses first (SQLite checks RESTRICT row by row inside the cascade).
- `POST /api/projects/{id}/versions/from-patch` `{name, notes?, base?: "draft" | {version_id}, patch: {dotted.path: value}}` → 201 version. Paths are existing leaves of the design document; a `mission.` prefix patches the mission. The patched documents pass the same validation as a draft save (422 plain message otherwise, 409 for a taken name). Parent: the base version, or the version the draft is based on. The draft is not changed.
- `GET /api/validation` → `{report | null, source: "app" | "snapshot" | null, job: {status: idle|queued|running|done|error, progress, stage, queued_at, started_at, finished_at, error, trigger: startup|owner}}`; `"snapshot"` is the committed `docs/validation/latest.json`, served (source checkout only) until this server has its own report. `POST /api/validation/run` → 202 same shape (owner only). With no report at startup the suite runs once in the background (`VALIDATION_ON_STARTUP`, default true; about 20 s on a cold polar cache). The snapshot is refreshed by `tests/validation/test_validation.py`.

**Settings schema 2.** `checks.manoeuvre_load_factor` (1-10), `checks.structural_safety_factor` (1-5), `checks.transition_thrust_margin_min` (1-5), `analysis.ncrit` (1-14), each with label, description and source in `meta`; upgrader 1→2 in `app/schemas/migrate.py`; a v1 document sent to `PUT` is upgraded, not refused. Stored rows keep only true overrides. Analyses receive the owner's merged settings document and `settings_meta` (the `meta` labels and sources) so every check names its threshold source.

**Assistant** (`app/assistant/chat.py`, `tools.py`, `app/routers/assistant.py`). Tools take `[{path, value}]` lists (strict schemas cannot describe a free-form map) and the server builds the patch. `propose_change` validates the patch against the draft and makes the server emit a `proposal` event; its tool result is only "shown". One thread per project; `assistant_messages` stores each Messages API turn verbatim (`content`) plus UI-only `meta`; refusals and errors are stored as `notice` rows that are never sent to Claude.
- `GET /api/assistant/status` → `{available, model, message, max_tool_calls}`.
- `POST /api/projects/{id}/assistant/messages` `{text}` (1-4000 chars) → `text/event-stream`; before streaming: 503 `{detail}` without a key, 409 when an answer is already running in the project. Events: `text {text}`, `tool_call {id, name, label}`, `proposal {patch, summary, base: "draft"}`, `done {message_id, stop_reason, tool_calls, model, usage}`, `error {message, code: refusal|max_tokens|budget|api_error|busy|internal}`; the stream ends after `done` or `error`. Text streamed before an `error` with code `refusal` is not part of the stored conversation.
- `GET /api/projects/{id}/assistant/messages` → `{thread_id, available, messages}` with `{id, role: "user", text, created_at}`, `{id, role: "assistant", text, tool_calls: [{id, name, label, is_error}], proposals: [{patch, summary, base}], created_at}` (one per answer, tool steps merged) and `{id, role: "notice", text, code, created_at}`. `DELETE` → 204.
- Budgets per owner message: 6 tool calls (more get an error result telling Claude to answer), 10 model requests, 60 000 output tokens, 16 000 `max_tokens` per request.
- Test seam: `CLAUDE_FAKE_CHAT_FILE` (ignored in production) replays a script; `backend/tests/fixtures/chat_fake_script.json` makes one `run_quick_analysis` call (wingspan 1900 mm), answers quoting the before/after endurance from the tool result and calls `propose_change`, then closes.
